# Database migrations

Migration filenames use a unique four-digit order and lowercase description. Once applied, a SQL file is immutable: the runner records its SHA-256 checksum and rejects edits. Add a new numbered migration for ordinary schema changes.

Phases 6A and 6B rewrite the pre-release baseline for disposable local development. The affected definitions include 0001, 0004–0009, 0013 and 0015. Existing Phase 6 checksums are intentionally rejected. After confirming the target, reset only the disposable local database using the [run guide](../plans/peergit-run.md#9-stop-inspect-and-reset), then run `go run ./cmd/migrate` twice. Leave applied non-disposable databases intact. There is no 0016 drop migration.

Run `go run ./cmd/migrate` explicitly after the database is available and before deploying application code. The API and worker never migrate on startup. Each migration and its history row commit in one transaction under a PostgreSQL advisory lock.

Migrations are forward-only by default. Before release, document the application rollback or forward repair alongside any migration that changes stored data. Do not run a reverse migration automatically; it can destroy data written by the new application version.

`0004_identity_campus_media.sql` defines campus tenants/domains, GitHub numeric identities and single-use PKCE login state, hashed server sessions that may have no campus, independent campus email challenges and reviews, campus roles, email-bound invitations, organizations, profiles/skills, versioned consent, encrypted-MFA storage, database rate-limit buckets, upload intents, and tenant-aware media metadata. PeerGit is still pre-production: the user explicitly authorized rewriting this migration definition and resetting only the disposable local PostgreSQL fixture volume for the GitHub signup refactor. Do not apply this reset procedure to staging or production. After the first supported release, treat applied migration definitions as immutable.

`0005_projects_recruitment.sql` defines campus projects and student collaboration openings, applications, memberships and team invitations. Ordinary projects retain these workflows and their audit and notification records. PBL projects use the academic roster and private or campus-card visibility. The typed project context scopes repository bindings and prevents student-role or invitation rows for PBL projects. Ordinary GitHub imports and recovery retain their existing IDs and installation relations through 0006–0009.

`0010_resend_campus_email.sql` adds provider/message metadata to campus deliveries and durable tables for Resend webhook receipts and keyed recipient suppressions. Existing SMTP delivery rows remain readable with null provider metadata. The application rollout must retain compatibility with these nullable columns.

`0011_daily_collaboration.sql` adds tenant-scoped project updates, threaded comments, reactions, discussions, milestones, tasks, assignees, task history, follows, bookmarks, and content reports. Writes append audit and `project.activity` outbox events within the same transaction. The API applies optimistic versions and bounds text, collection sizes, and reply depth. This phase does not add attachments, realtime delivery, collaborative editing, or imported GitHub issue mirroring.

`0012_durable_notifications.sql` adds tenant-scoped inbox records, per-user replay cursors, email preferences, provider attempts and message IDs, bounded SSE connection leases, and 90-day inbox retention. Notification inbox and eligible email jobs are created in one transaction by the `project.activity` outbox handler; email content is generic and contains no project source or private message text. Application decision email is enabled by default and cannot be disabled; project activity email is opt-in. Forward repair must preserve notification sequence uniqueness and provider idempotency keys.

`0013_scoped_messaging_discovery.sql` adds project, accepted-application and PBL room context fields with separate keys, participants, idempotent messages, user blocks, reports, tenant-filtered search indexes and a reproducible WACP ledger. PBL room reads and writes recheck current academic authority through the views in 0015. Inbox notices contain no message text. Profile search requires `profile_discovery` consent.

`0014_portfolios_succession.sql` adds selected portfolio evidence, hashed expiring/revocable share grants, typed project and organization handover requests, and explicit organization ownership. Portfolio reads filter every selected project against current consent, membership, lifecycle, publication and provider access; print uses an accessible browser-rendered view without storing a PDF. Handover changes only PeerGit ownership: a GitHub import's upstream owner and repository remain unchanged and are reported as such. User deletion for a current organization owner must be handled through succession before deletion because ownership is retained by a tenant-safe FK.

`0015_academic_mentorship_programs.sql` adds verified faculty profiles, separately invitation-scoped external mentor profiles and bounded engagements, courses/terms/cohorts/assignments, project endorsements, research/program calls and reviews, program cohorts/milestones/outcomes, academic digests/exports, and mentorship-only conversations. PBL checkpoints are the only submission records that reference repository snapshots. General assignment briefs do not accept Git snapshot submissions or evaluations. External mentors are never inserted into campus membership; access checks use the active college-scoped mentor grant and accepted engagement at request time. Exports are bounded, tenant-scoped, formula-safe CSV records with integrity hashes and seven-day expiry.

Phase 6A adds per-subject/per-term registrations, confirmed rosters, current faculty authority, team and faculty rooms, idea decisions, named attendance, private native Git provisions and credentials, authenticated push observations, and exact-SHA checkpoint receipts. Phase 6B constrains snapshots to confirmed PBL teams and native Forgejo bindings, removes generic academic submission/evaluation tables, and removes ordinary snapshot routes and jobs. Compound foreign keys keep PBL rows within the campus and prevent duplicate active roster placement and a second provision for the same team. This is a disposable local baseline; see [Phase 6B](../plans/implementation-phases.md#phase-6b-pbl-only-snapshots) before resetting or applying the rewritten migration files.
