# Database migrations

Migration filenames use a unique four-digit order and lowercase description. Once applied, a SQL file is immutable: the runner records its SHA-256 checksum and rejects edits. Add a new numbered migration for ordinary schema changes.

Run `go run ./cmd/migrate` explicitly after the database is available and before deploying application code. The API and worker never migrate on startup. Each migration and its history row commit in one transaction under a PostgreSQL advisory lock.

Migrations are forward-only by default. Before release, document the application rollback or forward repair alongside any migration that changes stored data. Do not run a reverse migration automatically; it can destroy data written by the new application version.

`0004_identity_campus_media.sql` defines campus tenants/domains, GitHub numeric identities and single-use PKCE login state, hashed server sessions that may have no campus, independent campus email challenges and reviews, campus roles, email-bound invitations, organizations, profiles/skills, versioned consent, encrypted-MFA storage, database rate-limit buckets, upload intents, and tenant-aware media metadata. PeerGit is still pre-production: the user explicitly authorized rewriting this migration definition and resetting only the disposable local PostgreSQL fixture volume for the GitHub signup refactor. Do not apply this reset procedure to staging or production. After the first supported release, treat applied migration definitions as immutable.

`0005_projects_recruitment.sql` adds campus projects, tenant-safe team membership, links to the existing `skills` table from `0004`, clean-media associations, recruiting roles, versioned application decisions, and account-bound one-time team invitations. Project creation, lifecycle changes, role changes, applications, and team decisions append audit records; project/application notifications enter the PostgreSQL outbox in the same transaction. Deactivate project recruitment by closing its open roles when the lifecycle leaves `active`; reopening the project does not silently reopen those roles. The migration is unchanged by the signup refactor; rollback application images without dropping project history, and use forward repair for any written project/application data.
